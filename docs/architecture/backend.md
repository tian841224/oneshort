# 後端架構

OneShort 後端以 Go 與 Gin 實作，負責帳號與角色、隊伍名額、成員資格、公會配對及即時事件。設計重點是讓多人操作遵循同一套規則。

## 主要模組

| 模組 | 支撐的產品功能 |
| --- | --- |
| 帳號與角色 | Discord／代碼＋PIN 登入、多角色管理與帳號連結 |
| 隊伍 | 建團、查詢、職缺、申請、成員管理與參與紀錄 |
| 公會 | 成員、公告、聊天、公會隊伍與 BOSS 配對 |
| 攻略 | 任務攻略、合作小工具與共享進度 |
| 通知與即時通訊 | 聊天、狀態更新及個人通知 |
| 平台支援 | 公告、問題回報、統計與管理功能 |

請求依 HTTP 處理、業務規則、資料存取分層；隊伍與公會等模組透過明確的介面協作。

## 資料分工

- **PostgreSQL**：保存帳號、角色、公會、預約／公會隊伍、通知與參與紀錄等持久資料。
- **Redis**：處理公開即時隊伍的運作狀態、聊天、快取與即時事件傳遞。

即時房間與參與紀錄有不同生命週期，因此即使原房間已過期，登入玩家仍可在歷史頁看到查詢範圍內的參與摘要。

## 執行角色

| 角色 | 責任 |
| --- | --- |
| API | 接收查詢與操作，檢查權限及業務條件 |
| 即時通訊服務 | 將聊天、隊伍與公會事件推送給相關連線 |
| 事件轉送工作 | 將已記錄的資料庫事件送入即時事件流 |
| 背景工作 | 處理隊伍生命週期、統計與公會週期性配對 |

這些角色可依執行環境整合或分開運行，讓一般資料操作、長連線與背景工作各自有清楚責任。

## 支撐協作的設計

- **後端判斷資格**：加入、審核、踢人與公會操作皆依目前身分及權限檢查。
- **成員與職缺驗證**：提交操作時重新確認名額、角色與條件，處理同時申請或資料變動。
- **配對先預覽再確認**：手動配對可產生草案，確認成團時再檢查最新成員及職缺資料。
- **資料變更與事件協作**：持久業務流程使用 Transactional Outbox 搭配 Redis Streams 傳遞事件；即時隊伍及聊天依各自的儲存流程處理。

測試包含 Go 單元、資料庫／Redis 整合及並行操作情境。這份公開摘要不展開部署與內部設定。
