# 互動與資料流

OneShort 透過 HTTP 完成查詢與操作，再用 WebSocket 通知相關玩家更新畫面。以下用三個實際情境說明。

## 申請加入隊伍

1. 玩家選擇角色與職缺，送出加入申請。
2. 後端確認角色、隊伍狀態、名額與加入條件。
3. 可直接加入時回傳結果；需要審核時，先進入待審狀態。
4. 房主核准後，相關玩家收到狀態更新，隊伍名單與個人申請同步更新。

前端依每筆操作的實際結果呈現畫面。若一次選擇多個角色，可能有的成功、有的失敗，不把整批選取視為全部入隊。

## 公會 BOSS 配對

1. 成員儲存每個角色的 BOSS 順位、時段與本輪參與設定。
2. 配對依目前成員、有效角色、可參加時段與職缺需求建立計畫。
3. 幹部先試算，再建立及調整草案。
4. 確認時重新驗證資料，成功後建立公會隊伍並通知相關成員。

預覽不是名額保留。角色停用、成員離會或其他隊伍安排，都可能影響最後結果。

## 攻略工具一起操作

1. 隊員在支援的組隊任務中開啟攻略或合作小工具。
2. 勾選、分工或進度變更送往後端。
3. 後端檢查成員資格與資料版本，回傳共享狀態。
4. 隊友的工具畫面接收更新；遇到衝突時重新取得狀態。

共享的是任務內容與進度，個人視窗位置則由各自的介面管理。

## 即時更新的分工

```text
玩家操作 → HTTP API → 規則檢查與資料更新 → 操作結果
                              ↓
                         即時事件傳遞
                              ↓
                     WebSocket → 相關玩家畫面
```

部分持久資料變更會在資料庫交易中同時記錄待傳送事件，再轉送到 Redis Streams；即時隊伍與聊天採用各自的處理流程。不同情境不共用單一跨儲存交易。

前端結合即時事件、歷史查詢與定期更新來維持狀態。通知中心與參與紀錄也提供重新進站後可查詢的資訊；不把一次即時推送視為永久送達紀錄。
